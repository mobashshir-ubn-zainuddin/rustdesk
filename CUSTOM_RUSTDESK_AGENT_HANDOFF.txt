**Agent prompt: build a custom-branded RustDesk Windows client, validate it, then offer precise development-environment cleanup**

Read this entire prompt before making changes. This is a reusable engineering recipe, not a transcript, a transfer of another person's app installation, or a statement about this computer's existing configuration. Build a new client from the official source using this owner's chosen name and artwork.

**Ask for the app name and icon first**

Before applying branding or installing tools, explicitly ask the owner both questions:

1. **What exact custom application name do you want, including spelling and capitalization?** Do not assume a name from the workspace folder, this prompt's filename, another user's project, or a previous example.
2. **Which image should be used as the icon? Please provide the local path to your PNG/JPG, or attach the image if this interface supports attachments.** Do not reuse someone else's character, logo or artwork by default.

Wait for the name and artwork before making dependent changes. You may perform read-only environment checks while waiting. Once supplied, summarize the exact name and icon path and validate that they are usable. Do not repeatedly ask for an input already supplied explicitly for this project.

Use these placeholders consistently:

| Placeholder | Meaning |
| --- | --- |
| `APP_NAME` | The owner's chosen application name, never a literal default brand |
| `APP_EXE` | The matching executable filename, normally `APP_NAME.exe` |
| `APP_NAMESPACE` | The app-data/extraction namespace actually derived by upstream code; inspect it rather than guessing |
| `ICON_INPUT` | The owner's actual artwork path |
| `CustomClientProject` | An example project folder; choose a suitable approved location |
| `C:\CustomClientBuild` | An example dedicated temporary tool root; check that it does not contain unrelated files |
| `client` | The source checkout folder in this recipe; not the product name |

Tokens inside Rust, CMake, resource and text examples must be replaced with properly escaped chosen values before compiling. PowerShell variables such as `$AppName` must be initialized from those confirmed inputs. Never execute placeholder paths literally. Validate the name against Windows filename rules, reserved names, and the CMake target rules used by this source. If it needs a different filesystem/target spelling, explain the constraint and agree that mapping with the owner before changing it; do not silently choose a different brand. The simplest tested naming route uses one valid name for APP_NAME, the CMake binary target and the executable stem. Names requiring separate display, target and executable names need additional inspection and validation.

In Rust, `config::APP_NAME` is an existing upstream identifier and must stay exactly as written. Replace the quoted `"APP_NAME"` placeholder value, not the identifier. The same distinction applies to other technical source names that happen to resemble placeholders.

**The assignment**

Build a Windows x64 RustDesk client with the chosen name and custom icon. Preserve remote-support functionality, server compatibility, authentication, consent prompts, visible session indicators, copyright/license notices and upstream attribution. Keep a clear description such as `APP_NAME Remote Support (RustDesk)`. Leave technical protocol/library identifiers intact. Do not perform a global replacement of every occurrence of RustDesk.

A free source build can use an existing free self-hosted RustDesk server; Server Pro is not required for this route. The connecting participant can normally keep a compatible standard client. Verify that expectation with a real consented connection test rather than promising compatibility in advance.

Do the engineering work within your available tools and permissions, including environment setup, focused source changes, compilation, complete packaging and validation. Explain the actual permission points. Windows UAC prompts may require the owner's interaction. Keep updates useful during long downloads/builds and report failures honestly.

After the owner confirms the connection test succeeded, inventory the development files/tools and ask for cleanup instructions with a concrete keep/remove list and space estimate. Only after cleanup is authorized, uninstall project-added development components and remove verified temporary files while preserving the app, settings, identity, shared runtimes and requested recovery backups.

**4. Enter the correct native environment in each new build shell**

Implement or adapt `enter-build-env.ps1` with the behavior below; inspect it before use. With the standard project layout, from the source checkout:

Its order matters: locate a compatible Visual Studio instance using `vswhere`, import the Developer PowerShell module, and enter the amd64 host/target environment first. Then set the task-local variables, because Developer PowerShell can overwrite `VCPKG_ROOT`.

```powershell

$env:RUSTUP_HOME = Join-Path $toolsRoot 'rustup'
```

```powershell
Copy-Item -LiteralPath .\target\release\rustdesk-portable-packer.exe -Destination $releaseExe -Force
```

**16. Cleanup scope and retention policy**

Use actual measurements from this computer. The following categories explain the intended cleanup; they are not permission to delete an unverified example path:

| Category | Cleanup treatment |
| --- | --- |
| Dedicated temporary tool root, e.g. `C:\CustomClientBuild` | Remove after registered in-root products are uninstalled, backups verified and no required project process uses it |
| Project source checkout and generated build output | Remove only after preserving a verified current source archive and any requested owner edits |
| Generated branding previews and project-only review artifacts | Remove if included in the approved manifest and needed inputs are retained |
| Project-added Visual Studio C++ Build Tools instance | Use its registered uninstaller for that exact instance; preserve pre-existing instances |
| Project-added SDK/SDK AddOn/LLVM | Use registered uninstallers where applicable; re-query shared/component ownership first |
| Standalone Visual Studio Installer introduced by setup | Consider removal only when no remaining instances need it |
| Installed custom app and its DLLs/assets | Keep intact; verify all recorded file hashes before/after cleanup |
| App settings, identity, keys, logs and active app-data/extraction directory | Preserve; do not confuse app data with a disposable build cache |
| Shared Visual C++ Redistributables and unrelated Windows Kits files | Preserve unless independently confirmed to be project-only and explicitly in scope |
| Complete EXE, compact source archive, checksums and brief build report | Ask the owner which recovery backups to keep |
| Pre-existing tools, unrelated projects, personal files and private configuration | Exclude from cleanup |

Build space and installed-app space are different categories. Do not promise an 80 MB maximum total footprint: settings, logs, shared runtimes, portable extraction and selected recovery backups can add to the app directory size. Report those separately. A small retained source archive plus a complete executable can make future recovery easier without retaining tens of gigabytes of SDKs and generated output.

Do not delete a portable extraction directory as a presumed duplicate. Confirm whether it is active, whether it contains unique files/settings, and whether the owner authorized its removal. The installed and extracted runners may differ, so compare complete contents rather than relying on the folder name or size.

Cleanup must not silently stop a working app, change its service startup preference or undo the owner's settings. Record the pre-cleanup state and preserve it. If registered uninstallers leave shared or older components, document the small residual rather than forcing a broad system purge.
